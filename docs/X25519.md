# Native X25519

`src/x25519.zen` implements experimental native X25519 following [RFC 7748 sections 5 and 6.1](https://www.rfc-editor.org/rfc/rfc7748#section-5). It contains the Montgomery ladder and field arithmetic in Zen. It calls no external cryptographic implementation and allocates no memory internally.

This implementation has functional tests, not a security audit or a production constant-time guarantee. It has not been benchmarked against optimized X25519 implementations.

## API and ownership

```zen
x25519_public_key = (
    output: Ptr<u8>, capacity: usize, private_key: Ptr<u8>,
    scratch: Ptr<u64>, scratch_words: usize
) bool

x25519_shared_secret = (
    output: Ptr<u8>, capacity: usize, private_key: Ptr<u8>, peer_public: Ptr<u8>,
    scratch: Ptr<u64>, scratch_words: usize
) bool
```

- Each input spans 32 readable bytes; `output` has at least 32 writable bytes. Input lengths are pointer contracts, not separately validated lengths.
- Scratch has at least **352 aligned `u64` words (2816 bytes)**, disjoint from every input and output span. Allocate it with an explicit alignment, for example `a.raw(2816, 8).try().to<u64>()`.
- Output may overlap either input, including partial overlap. Inputs are consumed before writing output. On success exactly 32 output bytes are written; disjoint input buffers remain unchanged.
- Null pointers, output capacity below 32, and scratch capacity below 352 return `false` before modifying output or scratch.
- A computed all-zero shared secret returns `false` without modifying output. Scratch is modified on this failure path.
- All memory stays caller-owned; no pointer is retained after return. Scratch contains secret intermediates afterward and is **not securely erased**. Concurrent calls require separate scratch buffers.

The implementation clamps a private copy of the scalar, masks the received public key's top bit, accepts noncanonical public encodings as required by RFC 7748, and emits canonical little-endian results. It rejects all-zero shared secrets, including low-order public inputs. It does not generate private keys: callers must supply fresh cryptographically secure random bytes when creating ephemeral keys.

X25519 by itself does not authenticate a peer. A protocol must bind its shared secret to the authenticated transcript and derive traffic keys through its specified KDF. Adding this primitive alone does not establish TLS forward secrecy; the handshake must negotiate and validate the corresponding ephemeral exchange.

## Arithmetic and limits

Field elements use 17 radix-2^15 limbs modulo `2^255 - 19`. Inputs to each arithmetic operation are canonical. A multiplication accumulator contains at most 17 products of limbs below 32768, so each coefficient is below `2^35`. Folding upper coefficients by 19 remains below `2^39`, fitting `u64`. Subtraction adds twice the field modulus before subtracting, avoiding unsigned underflow. Three fixed carry passes normalize intermediate values, followed by canonical reduction.

The ladder runs 255 iterations. Conditional swaps use integer arithmetic without a scalar-bit branch. Fermat inversion uses a fixed public exponent and iteration schedule. These source properties do not prove constant-time machine code, eliminate all side channels, or guarantee secure erasure. No production deployment claim is made.

Field operations use wrapping arithmetic only where the bounds above exclude
overflow. Scalar-bit extraction and output encoding use shifts instead of
division with secret-derived numerators. In a Linux x86_64 Clang `-O3` check,
the emitted executable contained no `div`/`idiv` instructions; a Valgrind
secret-taint run reported one remaining branch at all-zero shared-secret
rejection. These checks cover one compiler and machine-code path, not a
portable timing guarantee.

## Validation

The build target `test-x25519` runs standalone RFC known-answer, alias, rejection, invalid-argument and 1/1,000-iteration checks without Python or an external crypto library. The default `scripts/check.sh` also runs `scripts/check-x25519.py`; the latter requires the Python test dependencies from `tests/requirements.txt`.

```sh
ZEN_COMPILER=../zen-crypto-numeric/zen \
ZEN_STD=../zen-crypto-numeric/src \
python3 scripts/check-x25519.py
```

The differential runner includes 252 successful vectors in five output alias modes, 14 rejected inputs in three alias modes, 11 invalid argument cases, all combinations of the scalar bits changed by clamping, public-coordinate boundary/noncanonical cases, and the RFC 1/1,000-iteration vectors. It tests both optimized and UBSan builds against fixed published answers and Python `cryptography` reference results. The million-iteration vector is not run.

The emitted executable is checked for external crypto symbols. A deliberately corrupted Montgomery constant must fail the known-answer tests. Reference cryptography runs only in the test generator; it is not linked into the Zen implementation.
