What the server checks demonstrate
  - Independent Python verifies the server X25519 share, transcript, Finished
    and encrypted response using cryptography/HMAC test references.
  - Invalid ClientHello cases cannot provoke a server handshake flight;
    invalid client Finished/application-before-Finished cases cannot cause
    application data to be sent. Rejected calls preserve caller output.
  - OpenSSL s_client and the native client both receive a 50000-byte response
    over four records and authenticate close_notify; partial reads are tested.
  - Both directional traffic keys/sequences are exercised by independent and
    native peers. No external crypto backend calls appear in native symbols.
  - Null private input and private bytes equal to public random are rejected
    before allocation/I/O. Caller private inputs remain unchanged.
  - Two aligned allocations are released exactly once on success/refusal.

Transport boundary
  The Zen fixture connects TCP to the Python harness, then acts as TLS server.
  OpenSSL/native-client runs use a byte-only relay between connected sockets.
  These are real TLS server-role handshakes; they do not validate a native
  bind/listen/accept API or an HTTP listener integration.

Limitations
  Narrow external-PSK X25519 profile only: no PKI, hostname validation, HRR,
  ALPN, HTTP/2 negotiation, or general HTTPS interoperability claim.
  Sanitizers and peer agreement are not a security audit, constant-time proof,
  guaranteed secure erasure, full compiler aggregate result, or benchmark.
